# AGENTS.md

## 1. Цель проекта

Разработать MVP ИИ-помощника менеджера проектов.

Гипотеза:

> ИИ-помощник способен автоматически превращать поток входящих писем и сообщений в актуальное состояние проектов и предлагать менеджеру следующие действия, сокращая время работы менеджера и позволяя менеджеру успешно вести больше проектов за то же время.

На первом этапе источник данных — реальная почта одного пользователя.

**Основной источник для MVP — Яндекс.Почта (`yandex.ru`).**

Система должна регулярно получать новые письма, анализировать их, определять принадлежность к проекту, определять смысл события, обновлять состояние проекта и, если необходимо участие менеджера, предлагать действие или вариант ответа.

------

## 2. Основная схема

Реализовать архитектуру:

```text
Источник
  ↓
Нормализованное Message
  ↓
Hermes Agent
  ├── classification
  ├── project identification
  ├── context retrieval
  ├── event detection
  ├── manager participation decision
  └── draft generation
  ↓
Structured Agent Result
  ↓
Laravel validation
  ↓
Project State / Manager Action
```

Кратко:

```text
Hermes
  ↓
«Я считаю, что произошло X»
  ↓
Laravel проверяет
  ↓
Laravel применяет изменение
```

Не связывать почтовую интеграцию напрямую с бизнес-логикой проекта.

Каждый внешний источник должен преобразовываться во внутреннее нормализованное сообщение (`Message`).

В будущем должна быть возможность добавить другие источники:

- Gmail
- Outlook
- Telegram
- WhatsApp
- Redmine
- Jira
- другие системы

без переписывания основной бизнес-логики.

------

## 3. Главный принцип MVP — Hermes

**Hermes** — ограниченный агент анализа писем. Он предлагает, Laravel решает и пишет.

### Hermes может

- читать письмо;
- получать контекст (диалог, проект, инструкции, недавние события);
- искать / сопоставлять проекты (в т.ч. через детерминированные правила как tools);
- анализировать письмо;
- предлагать изменение состояния (через Event);
- формировать draft ответа;
- создавать поля предложения менеджеру (`ManagerAction`).

### Hermes не может

- самостоятельно отправить письмо;
- удалить письмо;
- изменить критичные данные без валидации Laravel;
- выполнять произвольные команды на сервере.

Hermes **не** изменяет базу данных напрямую.

Hermes формирует **Structured Agent Result**.

Затем приложение:

1. валидирует результат;
2. проверяет допустимость действий;
3. преобразует результат в доменное событие (`Event`);
4. изменяет состояние проекта через обычную бизнес-логику;
5. при необходимости создаёт `ManagerAction`.

Hermes — компонент анализа и подготовки предложений, а не источник истины.

Стек вызова LLM:

```text
Hermes
  │
  └── LlmProvider
         │
         └── Gemini Flash   (MVP; сменяемый)
```

Бизнес-логику не привязывать к Gemini: меняется только `LlmProvider`.

# 5. Основные сущности

Минимально предусмотреть следующие сущности.

## User

Пользователь системы.

На MVP используется один пользователь, но архитектура не должна быть жёстко привязана к одному пользователю.

------

## Project

Проект менеджера.

Минимальные данные:

- id
- name
- description
- status
- instructions
- created_at
- updated_at

Проект должен иметь настройки, позволяющие описать особенности обработки писем.

Например:

- какие адреса относятся к проекту;
- какие домены относятся к проекту;
- какие темы писем относятся к проекту;
- какие ключевые слова могут использоваться;
- какие технические уведомления относятся к проекту;
- какие правила обработки действуют на проекте.

Не ограничивать идентификацию проекта только email-адресом.

------

## ProjectInstruction

Если для удобства архитектуры инструкции лучше вынести из Project в отдельную сущность — сделать это.

Инструкция должна позволять менеджеру описывать особенности проекта для AI.

Например:

```text
Клиент проекта — ООО Ромашка.

Основные контакты:
client@example.com

Письма с домена example.com обычно относятся к проекту.

Redmine уведомления с определённого проекта также относятся к этому проекту.

Если клиент сообщает о критической ошибке — требуется участие менеджера.

Если письмо содержит только автоматическое уведомление о создании задачи — ответ менеджера обычно не требуется.
```

Инструкции должны храниться отдельно от системного промпта.

------

## ClientCompany (Клиенты)

Компания-клиент (не путать с classification=`client`).

- id, name, description, notes, timestamps
- M2M с `projects` через `client_company_project`
- hasMany `ClientContact` (каскадное удаление контактов)

Сервис: `App\Domain\Clients\ClientCompanyService`.

------

## ClientContact (Контакты)

Человек в компании-клиенте.

- принадлежит ровно одной `ClientCompany`
- ФИО: last_name, first_name, middle_name; position; emails (JSON); telegram; phone; notes
- M2M с `projects` через `client_contact_project`
- `fullName(): string` → «Фамилия Имя Отчество»

Правило: при привязке контакта к проектам **также** привязывается его компания (`syncWithoutDetaching`). Отвязка контакта **не** отвязывает компанию.

Сервис: `App\Domain\Clients\ClientContactService`.

------

## Executor (Исполнители)

Сотрудник нашей компании.

- ФИО, position, emails (JSON), telegram, phone, notes, is_active
- M2M с `projects` через `executor_project` (агрегат / справочник на проекте)
- M2M с `project_tasks` через `executor_project_task` (основная привязка исполнителей к задачам)
- `manager_executor_id` на `ProjectTask` — менеджер конкретной задачи (обычно «Автор» из Redmine)
- `fullName(): string`

Сервис: `App\Domain\Executors\ExecutorService`.
Ручное редактирование людей на задаче: `App\Domain\Tasks\ProjectTaskPeopleService`.

------

## Conversation

Логическая переписка.

Нужна для понимания контекста нескольких писем.

Связь:

```text
Project
  └── ProjectTask (задача: Redmine #id / Jira KEY / email thread)
        └── Message
  └── Conversation
        └── Message
```

`ProjectTask` — единица работы внутри проекта. Redmine/Jira: один тикет = одна задача (много уведомлений). Клиентская почта без тикета: один `Conversation` ≈ одна задача (`source=email_thread`).

Дополнительно: `agent_state` (JSON) — сжатая память диалога для Hermes (`topic`, `status`, `open_questions`, `commitments`, `waiting_for`, `last_summary`, …). Пишет Laravel после валидации Hermes (`UpdateConversationAgentMemory`), не сам LLM напрямую.

У `Project` также есть `agent_state` (JSON) — сжатое состояние проекта (`topic`, `waiting_for`, `open_questions`, `last_summary`, …). Пишет `UpdateProjectAgentState` после Hermes; на карточке проекта в Orchid — блок только для чтения.

------

## Message

Нормализованное входящее сообщение.

Не хранить только данные конкретного почтового провайдера.

Минимально предусмотреть:

- source
- external_id
- conversation_id
- sender
- recipients
- cc
- subject
- body
- received_at
- headers / metadata
- classification
- processing status
- ai_summary / ai_confidence
- agent_facts (JSON) — факты письма для агента (topic, open_questions, key_points, waiting_for, …)
`external_id` должен позволять безопасно повторно синхронизировать Яндекс.Почту без создания дубликатов.

При необходимости хранить исходные технические данные письма отдельно.

------

## Event

Результат понимания сообщения.

Event описывает не само письмо, а то, что произошло.

Например:

```text
client_question
client_request
client_reported_bug
client_approved
client_rejected
task_created
task_updated
task_completed
technical_notification
information_only
```

Набор event types не должен быть чрезмерно большим на MVP.

------

## ManagerAction

Предложенное действие для менеджера.

Например:

```text
no_action
review
reply
follow_up
```

Действие должно иметь статус:

```text
pending
approved
edited
rejected
completed
```

# 6. Классификация входящих писем

Это одна из ключевых частей MVP.

Почта пользователя может содержать:

- клиентские письма;
- Redmine;
- Jira;
- Aspro;
- уведомления сайтов;
- системные уведомления;
- рассылки;
- личную переписку;
- другие сообщения.

Система НЕ должна считать каждое письмо клиентским.

На первом этапе классифицировать письмо как минимум на:

```text
client
site_lead
technical
newsletter
personal
ignored
unknown
```

`site_lead` («Заявка с сайта») — формы с сайтов (обратный звонок, бронирование и т.п.): `SiteLeadMatcher` по доменам `classification.site_lead_domains` и темам `site_lead_subjects`. Не путать с `client` (живая переписка).

`ignored` («Игнорируемое») — глобальный чёрный список (Яндекс ID, пароли приложений, системный шум). Отдельно от `technical` (Redmine/Jira и другие проектные технические источники).

При необходимости классификация может быть расширена.

------

# 7. Идентификация проекта

Определение проекта выполнять в несколько этапов.

Не отправлять каждое письмо сразу в LLM со всеми проектами пользователя.

Сначала использовать детерминированные признаки:

- email отправителя;
- email получателя;
- домен отправителя;
- thread / conversation;
- subject;
- известные внешние идентификаторы;
- правила проекта;
- технический источник;
- headers.

После предварительного отбора передавать в AI только наиболее вероятные проекты.

Если проект определить нельзя:

```text
project_id = null
```

Не придумывать проект.

Сообщение должно попасть в очередь на ручную классификацию.

**Цепочка писем** — сущность `Conversation` (по `In-Reply-To` / `References` / Message-ID при импорте). Когда одно письмо в цепочке получает `project_id`, сервис `PropagateProjectToConversationMessages` привязывает тот же проект ко всем соседним письмам без проекта (кроме `ignored`), снимает `needs_manual` → `classified` и при необходимости ставит Hermes-анализ в очередь. Уже привязанные к другому проекту письма не перезаписываются.

------

# 8. Hermes-анализ (Structured Agent Result)

Hermes должен получать только необходимый контекст.

В контекст могут входить:

- письмо (latest reply без длинных цитат + опционально thread_excerpt);
- `conversation_agent_state` — сжатая память диалога;
- предыдущие сообщения текущего диалога (предпочтительно `ai_summary` / `agent_facts`, не полные тела);
- информация о проекте;
- инструкции проекта;
- последние релевантные события проекта (только по более ранним письмам);
- кандидаты проектов (после детерминированного отбора);
- analysis_corrections.

Не передавать весь почтовый ящик целиком.

Hermes должен возвращать строго структурированный результат (Structured Agent Result).

Пример:

```json
{
  "classification": "client",
  "project_id": 17,
  "confidence": 0.94,
  "event_type": "client_question",
  "summary": "Клиент спрашивает о сроках исправления ошибки",
  "requires_manager": true,
  "suggested_action": "reply",
  "draft_reply": "Добрый день! Проверяем проблему...",
  "reason": "Клиент ожидает информацию о сроках",
  "agent_facts": {
    "topic": "Сроки бага",
    "open_questions": ["Когда будет фикс?"],
    "commitments": [],
    "waiting_for": "ответ менеджера",
    "key_points": ["Клиент ждёт ETA"]
  }
}
```

`agent_facts` опционален: Laravel всё равно сохранит память из summary/reason через `UpdateConversationAgentMemory`.
Ответ Hermes обязательно валидировать в Laravel.

Если возвращается некорректный JSON или неизвестное значение enum — считать анализ неуспешным и сохранять ошибку обработки.

Детерминированные правила (классификация technical/ignored, точный email→проект) могут выполняться **до** или **как tools внутри** Hermes, чтобы не слать лишние запросы в LLM (§17, §22).

------

# 9. Confidence

Не считать confidence от AI объективной вероятностью.

Это только дополнительный сигнал.

Основная система должна иметь собственные правила принятия решений.

Например:

```text
высокая уверенность + детерминированное совпадение
→ автоматическое применение

низкая уверенность
→ ручная проверка
```

Конкретные пороги вынести в конфигурацию.

------

# 10. Изменение состояния проекта

Состояние проекта должно изменяться на основании нормализованных событий.

Пример:

```text
Message
 ↓
Hermes Agent
 ↓
Structured Agent Result
 ↓
Laravel validation
 ↓
Event: client_reported_bug
 ↓
Project state updated / ManagerAction
```

Не изменять Project непосредственно из класса Hermes / LLM.

Использовать отдельный application/domain service.

------

# 11. Предложения менеджеру

После обработки нового события система должна определить:

```text
нужно ли действие менеджера?
```

Если нет:

```text
No action
```

Если да — создать ManagerAction.

В одной переписке (`conversation` / `project_task`) одновременно остаётся только одно pending-действие — по самому новому письму. Более старые pending автоматически закрываются (`completed`) сервисом `SupersedeStaleConversationManagerActions`. Разовая зачистка: `manager-actions:supersede-stale` (кнопка в «Сервисные команды»).

Для ответа клиенту создать draft.

Менеджер должен иметь возможность:

1. посмотреть исходное письмо;
2. увидеть проект;
3. увидеть краткую сводку;
4. увидеть, что понял AI;
5. увидеть предложенное действие;
6. увидеть draft ответа;
7. изменить draft;
8. подтвердить;
9. отклонить предложение.

AI не должен самостоятельно отправлять письмо в MVP.

# 12. Интерфейс MVP

Админка MVP — **Orchid Platform** (`orchid/platform` ^14.53), префикс `DASHBOARD_PREFIX=/admin`.

Интерфейс админки на **русском** (`APP_LOCALE=ru`, `APP_FALLBACK_LOCALE=ru`).

Публичный сайт (`/`) — пустая страница (как rbi2025 public), без редиректа в админку.

Не создавать отдельный сложный frontend и не возвращать Blade-админку.

Нужны Orchid-экраны:

## Dashboard (`/admin`)

Показывать:

- счётчики: всего писем, pending, needs_manual, unknown, ignored, события/письма требующие внимания, pending ManagerAction, число проектов;
- быстрые ссылки на pending actions, needs_manual сообщения и игнорируемые.

------

## Projects

CRUD проектов в Orchid.

Для проекта:

- название;
- описание;
- статус;
- инструкции;
- правила сопоставления писем (textarea, один пункт на строку → массивы через `ProjectService`);
- список связанных сообщений;
- список задач (`ProjectTask`);
- список событий;
- связанные клиенты / контакты (read-only);
- менеджеры и исполнители — **read-only агрегаты с задач** проекта (не выбираются на карточке проекта).

------

## Задачи

Список `ProjectTask` (`platform.tasks`, `/admin/tasks`), пункт меню «Задачи» рядом с «Проекты».

Фильтры: проект, источник (Redmine/Jira/Aspro/переписка), статус.
Карточка задачи (`platform.tasks.view`): ключ, проект, статус, **менеджер задачи** (`manager_executor_id`), **исполнители задачи** (M2M `executor_project_task`, редактируются), связанные письма.
С карточки проекта — таблица задач (с колонкой менеджера); из списка — ссылки на письма (`filter[project_task_id]`).

`ProjectTaskSource::Aspro` — уведомления Aspro.Cloud (`Уведомление …` / `Уведомление Задача: …`); ключ — hash нормализованного title (`ProjectTaskKeyExtractor`).

Сервис ручного назначения людей: `App\Domain\Tasks\ProjectTaskPeopleService`.

------

## Клиенты / Контакты / Исполнители

Справочники Orchid (меню «Справочники»):

- Клиенты (`platform.client-companies`) — CRUD компаний, контакты на карточке, multi-select проектов;
- Контакты (`platform.client-contacts.*`) — CRUD под компанией;
- Исполнители (`platform.executors`) — CRUD + is_active + проекты.

------

## Inbox / Events

Список нормализованных сообщений.

Для каждого:

- отправитель;
- тема;
- дата;
- классификация;
- проект;
- summary;
- event type;
- requires manager;
- confidence;
- processing status.

Должна быть возможность вручную изменить:

- классификацию;
- проект;
- результат анализа (с записью в `analysis_corrections`).

Экран **«События»** (`platform.events`, `/admin/events`, меню «Работа» рядом с «Действия менеджера»):
список `Event` (фильтры project / type / applied), колонки id→письмо, type, summary (полный), project, message, confidence, applied_at, created_at.
Опционально карточка `platform.events.view`.

**Заявки с сайта (site leads):** темы вроде «Заявка на обратный звонок» / «Заявка на бронирование» с доменов `classification.site_lead_domains` (в т.ч. rbi.ru) → `SiteLeadMatcher` → classification=`site_lead` (не ignored и не client), до blacklist `noreply@`. Hermes / AnalyzeMessage: `event_type=site_lead`, `requires_manager=true`. Stop-words заявок удаляются из `MailFilterSettingSeeder`.

Экран **«Распределение по проектам»** (`platform.messages.assign`, `/admin/messages/assign`):
группирует нераспределённые письма по кандидатам `ProjectMatcher` (порог `project_match_suggest_threshold`, без LLM),
массовая привязка и создание проекта + привязка (`SuggestUnassignedMessageAssignments`, `BulkAttachMessagesToProject`).
Ссылка в commandBar входящих и пункт меню «Распределение» под «Почта».

Hermes LLM вызывается для:
- `client` / `site_lead` / `unknown` с `project_id` **или** с кандидатами `ProjectMatcher` (ambiguous/unmatched);
- `technical` с известным `project_id` (режим `technical_summary` — краткий summary без draft).

В контекст Hermes также входят `analysis_corrections` письма и недавние правки по проекту.

Ежедневно (scheduler) `DetectClientFollowUpsJob` создаёт `ManagerAction` типа `follow_up`, если последнее письмо в диалоге — клиентское и старше `ai.follow_up.silence_days` (по умолчанию 3). CLI: `messages:detect-follow-ups`.

Экран **«Сервисные команды»** (`platform.admin-tools`, `/admin/admin-tools`):
кнопки для artisan (`mail:sync`, `messages:reprocess`, `--apply-mail-filters`, `messages:detect-follow-ups`, `manager-actions:supersede-stale`, `projects:apply-people`, `projects:merge-duplicates`, `messages:repair-bodies`, `messages:purge-empty`, метрики) с описанием «что / когда»; результат в UI и в Журнале.

## Настройки

Singleton `app_settings` (`AppSetting` / `AppSettingService`), экран Orchid «Настройки» (`platform.settings`, `/admin/settings`):

- переключатель **автоматически создавать проекты (Redmine)** + порог уверенности;
- переключатель **автоматически распределять через LLM** (любые нераспределённые письма) + порог уверенности LLM.

Порядок при обеих галочках:

1. `ProjectMatcher` (правила);
2. `AutoCreateProjectFromIncomingMail` (Redmine, без LLM);
3. если проект всё ещё `null` — `AutoAssignProjectViaLlm` (привязка к существующему или создание по `proposed_name`, только если `confidence` ≥ порога);
4. `ResolveOrCreateProjectTask`, затем `ApplyRedminePeopleToProject`: из тела `Автор:` / `* Автор:` → менеджер **задачи** (`project_tasks.manager_executor_id` + executor на задаче и проекте), `Назначена:`/`Назначен:` → исполнитель **задачи** (`executor_project_task`); при пробелах — `ApplyPeopleToProjectViaLlm` (менеджер/исполнители по содержанию письма, без перезаписи уже заданного менеджера задачи);
5. если есть проект (или кандидаты для client/site_lead/unknown) — Hermes-анализ: summary / event / requires_manager / confidence;
6. тема с `(Обратная связь)` → `requires_manager=true` (+ ManagerAction, если Event ещё нет).

После включения галочек для уже классифицированных писем без проекта: `messages:reprocess --reclassify-unassigned` (кнопка в «Сервисные команды»). Queue worker периодически перезапускается (`--max-jobs=50`).

LLM проекты не создаёт в обход порога; ignored не обрабатывается.

# 13. Яндекс.Почта

Для MVP использовать **IMAP** как основной механизм получения писем.

Почтовая интеграция должна быть изолирована от остального приложения.

Создать отдельный интерфейс, например:

```php
interface MailProvider
{
    public function fetchNewMessages(): iterable;
}
```

Реализация для MVP:

```text
YandexMailProvider
```

В будущем должны быть возможны:

```text
YandexMailProvider
GmailProvider
OutlookProvider
```

без изменения доменной логики.

------

## Синхронизация

Реализовать периодическую синхронизацию Яндекс.Почты.

Использовать Laravel Scheduler.

Синхронизация должна быть идемпотентной.

Повторный запуск не должен создавать дубликаты сообщений.

Хранить внешний идентификатор сообщения и необходимые данные для определения уже обработанных писем.

Не скачивать весь mailbox при каждом запуске.

На MVP достаточно регулярно получать новые письма.

------

## Настройки подключения

Данные подключения к Яндекс.Почте не хранить в коде.

Использовать `.env` / Laravel configuration.

Например:

```env
MAIL_PROVIDER=yandex

YANDEX_IMAP_HOST=imap.yandex.ru
YANDEX_IMAP_PORT=993
YANDEX_IMAP_ENCRYPTION=ssl
YANDEX_IMAP_USERNAME=
YANDEX_IMAP_PASSWORD=
YANDEX_IMAP_FOLDER=INBOX
YANDEX_IMAP_SYNC_ALL_FOLDERS=true
YANDEX_IMAP_FOLDER_EXCLUDE=Spam,Junk,Drafts,Draft,Sent,Outbox,Спам,Черновик,Отправленн,Исходящ
YANDEX_IMAP_FIRST_SYNC_LIMIT=100
```

Синхронизация обходит **все папки** ящика (включая пользовательские и Корзину), у каждой свой `mail_sync_states.last_uid`. Исключаются спам/черновики/отправленные (см. `YANDEX_IMAP_FOLDER_EXCLUDE`). `YANDEX_IMAP_FOLDER` — стартовая папка для listing; при `SYNC_ALL_FOLDERS=false` синхронизируется только она.
Фактические параметры подключения проверить по актуальной документации Яндекс.Почты перед реализацией.

Не логировать пароль или другие секреты.

------

# 14. Очереди

Не выполнять длительный AI-анализ внутри HTTP request.

Использовать очереди.

При временных ошибках LLM (лимит Gemini 429, 5xx, сеть) `AnalyzeMessage` **не** ставит письмо в `failed` сразу: пишет `deferred` в журнал и повторно ставит `AnalyzeMessageJob` в очередь с backoff (`ai.queue.analyze_tries` / `ai.queue.analyze_backoff_seconds`, по умолчанию до 10 попыток: 1–30 мин). `failed` — только после исчерпания ретраев или при невалидном JSON / неизвестном enum.

Аналогично для **LLM-распределения по проектам** (`AutoAssignProjectViaLlm`): при 429 письмо **не** уходит в `needs_manual` сразу — статус `classified` + `RetryAutoAssignProjectViaLlmJob`. В «Требует ручной обработки» — только после того, как LLM реально отработала и не назначила проект (ниже порога / unmatched), либо после исчерпания ретраев.

Пример:

```text
Sync Yandex Mail
  ↓
Store Message
  ↓
Classify Message Job (= Hermes ProcessIncomingMessage)
  ├── classification + project identification (rules)
  ├── context retrieval
  ├── event detection + draft (LLM, если нужно)
  └── Laravel validation → Event / ManagerAction
```

Конкретное количество Job можно изменить, если это упрощает архитектуру.

# 15. Логирование

Для каждого сообщения должна быть возможность понять:

```text
когда получено
↓
когда классифицировано
↓
какой проект выбран
↓
какой AI-анализ выполнен
↓
какое событие создано
↓
изменилось ли состояние проекта
↓
создано ли предложение менеджеру
```

AI-запросы и ответы логировать таким образом, чтобы можно было отлаживать систему.

При этом не допускать утечки секретов и credentials в логи.

# 16. Hermes + LLM Provider

Не привязывать бизнес-логику к Gemini.

Слой агента:

```php
interface HermesAgent
{
    public function propose(Message $message): HermesProposal;
}
```

Слой модели (сменяемый):

```php
interface LlmProvider
{
    public function analyze(MessageContext $context): array;
}
```

На первом этапе `LlmProvider` = **Gemini Flash**.

В будущем заменить:

```text
Gemini Flash
→ OpenAI
→ Claude
→ другая модель
```

без изменения Project, Message, Event, ManagerAction и без изменения контракта Hermes.

`AiAnalyzer` — устаревший alias `LlmProvider` (совместимость); новый код зависит от `HermesAgent` / `LlmProvider`.

# 17. Стоимость AI

Не отправлять AI запросы без необходимости.

Использовать детерминированные правила там, где они достаточны.

Например:

```text
известный email отправителя
→ проект определяется без LLM
```

или:

```text
очевидное техническое уведомление
→ не требуется полный анализ клиентского контекста
```

AI использовать там, где требуется понимание содержания.

# 20. Критерий успеха MVP

```text
        ↓

```

Менеджер должен иметь возможность проверить и исправить результат.

# 21. Экспериментальные метрики

Система должна сохранять данные, позволяющие оценить гипотезу.

События пишутся в таблицу `hypothesis_metric_events` через `App\Domain\Metrics\HypothesisMetricsRecorder`
(например: `mail_received`, `mail_classified_client`, `project_auto_matched`, `project_unmatched`,
`project_ambiguous`, `event_requires_manager`, `draft_created`, `draft_approved_unchanged`,
`draft_edited`, `action_rejected`, `analysis_corrected`).

Агрегаты:

- Orchid: Dashboard (блок гипотезы) + экран «Метрики гипотезы» (`/admin/metrics/hypothesis`);
- CLI: `php artisan metrics:hypothesis-report` (`--json`, `--evaluate`) и `php artisan mailbox:evaluate`.

Минимально измерять:

- количество полученных писем;
- количество технических писем;
- количество клиентских писем;
- количество писем, для которых проект определён автоматически;
- количество писем без определённого проекта;
- количество корректно определённых событий;
- количество событий, требующих участия менеджера;
- количество ложных предложений;
- количество draft ответов;
- количество draft ответов, принятых без изменений;
- количество draft ответов, отредактированных менеджером;
- количество предложений, отклонённых менеджером.

Особенно важно сохранять факт изменения результата менеджером.

Например:

```text
AI:
project = Project A

Manager:
project = Project B
```

или:

```text
AI:
requires_manager = true

Manager:
requires_manager = false
```

Это позволит использовать реальные исправления менеджера для последующего улучшения правил и промптов.

# 25. Безопасность

Почтовые данные могут содержать конфиденциальную информацию.

- не хранить credentials в Git;
- использовать `.env`;
- не выводить пароли в логи;
- не отправлять в LLM данные, которые не нужны для анализа;

- валидировать все результаты AI перед записью в БД.

# 27. Definition of Done

MVP считается готовым, когда:

1. Реальная Яндекс.Почта подключается к системе.
2. Новые письма автоматически импортируются.
3. Повторная синхронизация не создаёт дубликаты.
4. Письма классифицируются.
5. Технические уведомления не считаются автоматически клиентскими.
6. Письма сопоставляются с проектами.
7. Для письма формируется нормализованное событие.
8. Состояние проекта может измениться на основании события.
9. Определяется необходимость участия менеджера.
10. При необходимости создаётся ManagerAction.
11. Для ответа создаётся draft.
12. Менеджер может изменить или отклонить результат.
13. Hermes / AI не отправляет письмо самостоятельно.
14. Все основные сценарии покрыты automated tests.
15. Есть журнал обработки, позволяющий понять, почему система приняла конкретное решение (в т.ч. шаги Hermes).
16. Собираются метрики, необходимые для оценки гипотезы.

------

# 28. Правило для coding agent

Не начинать сразу с написания большого количества кода.

Сначала:

1. проанализировать репозиторий;
2. определить существующие Laravel conventions;
3. определить отсутствующие компоненты;
4. проверить существующую структуру проекта;
5. создать `docs/IMPLEMENTATION_PLAN.md`;
6. описать предлагаемые модели, миграции, сервисы, jobs и интерфейсы;
7. показать план в конце первого этапа работы;
8. после этого реализовывать проект по Phase 1 → Phase 8.

Если обнаруживается архитектурное решение, которое противоречит этому документу, остановиться и явно описать проблему в плане вместо молчаливого изменения требований.

При изменении архитектуры coding agent обязан синхронно обновить AGENTS.md, docs/IMPLEMENTATION_PLAN.md и README.md.
В разработке нет backward compatibility: устаревший код/Blade/роуты удалять.
После существенных изменений функциональности — обновлять seeders и при необходимости `make fresh-seed`.
Качество: typed properties/enums, thin screens / fat services, обязательные tests, без секретов в логах.

Главный приоритет:

**рабочий проверяемый MVP > количество функций > архитектурная сложность.**
