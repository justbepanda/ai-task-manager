# AGENTS.md

## 1. Цель проекта

Разработать MVP ИИ-помощника менеджера проектов.

Гипотеза:

> ИИ-помощник способен автоматически превращать поток входящих писем и сообщений в актуальное состояние проектов и предлагать менеджеру следующие действия, сокращая время работы менеджера и позволяя менеджеру успешно вести больше проектов за то же время.

На первом этапе источник данных — реальная почта одного пользователя.

**Основной источник для MVP — Яндекс.Почта (`yandex.ru`).**

Система должна регулярно получать новые письма, анализировать их, определять принадлежность к проекту, определять смысл события, обновлять состояние проекта и, если необходимо участие менеджера, предлагать действие или вариант ответа.

------

## 2. Основная схема

Реализовать архитектуру:

```text
Источник
  ↓
Нормализованное событие
  ↓
Идентификация проекта / диалога
  ↓
Определение смысла
  ↓
Изменение состояния проекта
  ↓
AI-предложение менеджеру
```

Не связывать почтовую интеграцию напрямую с бизнес-логикой проекта.

Каждый внешний источник должен преобразовываться во внутреннее нормализованное событие.

В будущем должна быть возможность добавить другие источники:

- Gmail
- Outlook
- Telegram
- WhatsApp
- Redmine
- Jira
- другие системы

без переписывания основной бизнес-логики.

------

## 3. Главный принцип MVP

AI не должен напрямую изменять базу данных.

AI формирует структурированный результат анализа.

Затем приложение:

1. валидирует результат;
2. проверяет допустимость действий;
3. преобразует результат в доменное событие;
4. изменяет состояние проекта через обычную бизнес-логику.

AI является компонентом анализа и подготовки предложений, а не источником истины.

------

## 4. Технологии

Использовать:

- PHP
- Laravel
- MySQL
- Laravel Queue
- Laravel Scheduler
- PHPUnit / Pest в зависимости от существующего проекта
- IMAP для получения писем из Яндекс.Почты
- LLM API через отдельный абстрактный интерфейс

Не добавлять новые технологии без необходимости.

Если проект уже содержит существующую архитектуру, сначала изучить её и максимально использовать существующие решения.

# 5. Основные сущности

Минимально предусмотреть следующие сущности.

## User

Пользователь системы.

На MVP используется один пользователь, но архитектура не должна быть жёстко привязана к одному пользователю.

------

## Project

Проект менеджера.

Минимальные данные:

- id
- name
- description
- status
- instructions
- created_at
- updated_at

Проект должен иметь настройки, позволяющие описать особенности обработки писем.

Например:

- какие адреса относятся к проекту;
- какие домены относятся к проекту;
- какие темы писем относятся к проекту;
- какие ключевые слова могут использоваться;
- какие технические уведомления относятся к проекту;
- какие правила обработки действуют на проекте.

Не ограничивать идентификацию проекта только email-адресом.

------

## ProjectInstruction

Если для удобства архитектуры инструкции лучше вынести из Project в отдельную сущность — сделать это.

Инструкция должна позволять менеджеру описывать особенности проекта для AI.

Например:

```text
Клиент проекта — ООО Ромашка.

Основные контакты:
client@example.com

Письма с домена example.com обычно относятся к проекту.

Redmine уведомления с определённого проекта также относятся к этому проекту.

Если клиент сообщает о критической ошибке — требуется участие менеджера.

Если письмо содержит только автоматическое уведомление о создании задачи — ответ менеджера обычно не требуется.
```

Инструкции должны храниться отдельно от системного промпта.

------

## Conversation

Логическая переписка.

Нужна для понимания контекста нескольких писем.

Связь:

```text
Project
  └── Conversation
        └── Message
```

------

## Message

Нормализованное входящее сообщение.

Не хранить только данные конкретного почтового провайдера.

Минимально предусмотреть:

- source
- external_id
- conversation_id
- sender
- recipients
- cc
- subject
- body
- received_at
- headers / metadata
- classification
- processing status

`external_id` должен позволять безопасно повторно синхронизировать Яндекс.Почту без создания дубликатов.

При необходимости хранить исходные технические данные письма отдельно.

------

## Event

Результат понимания сообщения.

Event описывает не само письмо, а то, что произошло.

Например:

```text
client_question
client_request
client_reported_bug
client_approved
client_rejected
task_created
task_updated
task_completed
technical_notification
information_only
```

Набор event types не должен быть чрезмерно большим на MVP.

------

## ManagerAction

Предложенное действие для менеджера.

Например:

```text
no_action
review
reply
follow_up
```

Действие должно иметь статус:

```text
pending
approved
edited
rejected
completed
```

------

# 6. Классификация входящих писем

Это одна из ключевых частей MVP.

Почта пользователя может содержать:

- клиентские письма;
- Redmine;
- Jira;
- Aspro;
- уведомления сайтов;
- системные уведомления;
- рассылки;
- личную переписку;
- другие сообщения.

Система НЕ должна считать каждое письмо клиентским.

На первом этапе классифицировать письмо как минимум на:

```text
client
technical
newsletter
personal
unknown
```

При необходимости классификация может быть расширена.

------

# 7. Идентификация проекта

Определение проекта выполнять в несколько этапов.

Не отправлять каждое письмо сразу в LLM со всеми проектами пользователя.

Сначала использовать детерминированные признаки:

- email отправителя;
- email получателя;
- домен отправителя;
- thread / conversation;
- subject;
- известные внешние идентификаторы;
- правила проекта;
- технический источник;
- headers.

После предварительного отбора передавать в AI только наиболее вероятные проекты.

Если проект определить нельзя:

```text
project_id = null
```

Не придумывать проект.

Сообщение должно попасть в очередь на ручную классификацию.

------

# 8. AI-анализ

AI должен получать только необходимый контекст.

В контекст могут входить:

- письмо;
- предыдущие сообщения текущего диалога;
- информация о проекте;
- инструкции проекта;
- последние релевантные события проекта.

Не передавать весь почтовый ящик целиком.

AI должен возвращать строго структурированный результат.

Пример:

```json
{
  "classification": "client",
  "project_id": 17,
  "confidence": 0.94,
  "event_type": "client_question",
  "summary": "Клиент спрашивает о сроках исправления ошибки",
  "requires_manager": true,
  "suggested_action": "reply",
  "draft_reply": "Добрый день! Проверяем проблему...",
  "reason": "Клиент ожидает информацию о сроках"
}
```

Ответ AI обязательно валидировать.

Если AI возвращает некорректный JSON или неизвестное значение enum — считать анализ неуспешным и сохранять ошибку обработки.

------

# 9. Confidence

Не считать confidence от AI объективной вероятностью.

Это только дополнительный сигнал.

Основная система должна иметь собственные правила принятия решений.

Например:

```text
высокая уверенность + детерминированное совпадение
→ автоматическое применение

низкая уверенность
→ ручная проверка
```

Конкретные пороги вынести в конфигурацию.

------

# 10. Изменение состояния проекта

Состояние проекта должно изменяться на основании нормализованных событий.

Пример:

```text
Message
 ↓
AI analysis
 ↓
Event: client_reported_bug
 ↓
Project state updated
```

Не изменять Project непосредственно из AI-класса.

Использовать отдельный application/domain service.

------

# 11. Предложения менеджеру

После обработки нового события система должна определить:

```text
нужно ли действие менеджера?
```

Если нет:

```text
No action
```

Если да — создать ManagerAction.

Для ответа клиенту создать draft.

Менеджер должен иметь возможность:

1. посмотреть исходное письмо;
2. увидеть проект;
3. увидеть краткую сводку;
4. увидеть, что понял AI;
5. увидеть предложенное действие;
6. увидеть draft ответа;
7. изменить draft;
8. подтвердить;
9. отклонить предложение.

AI не должен самостоятельно отправлять письмо в MVP.

------

# 12. Интерфейс MVP

Не создавать сложный frontend.

Нужны следующие разделы.

## Dashboard

Показывать:

- новые события;
- события, требующие внимания;
- предложения AI;
- количество необработанных сообщений;
- сообщения без определённого проекта.

------

## Projects

CRUD проектов.

Для проекта:

- название;
- описание;
- статус;
- инструкции;
- правила сопоставления писем;
- список связанных сообщений;
- список событий.

------

## Inbox / Events

Список обработанных сообщений.

Для каждого:

- отправитель;
- тема;
- дата;
- классификация;
- проект;
- summary;
- event type;
- requires manager;
- confidence;
- processing status.

Должна быть возможность вручную изменить:

- классификацию;
- проект;
- результат анализа.

------

## Manager Actions

Очередь предложений AI.

Для каждого предложения:

```text
Проект
Событие
Почему требуется действие
Предлагаемое действие
Draft ответа
```

Кнопки:

```text
Подтвердить
Редактировать
Отклонить
```

------

# 13. Яндекс.Почта

Для MVP использовать **IMAP** как основной механизм получения писем.

Почтовая интеграция должна быть изолирована от остального приложения.

Создать отдельный интерфейс, например:

```php
interface MailProvider
{
    public function fetchNewMessages(): iterable;
}
```

Реализация для MVP:

```text
YandexMailProvider
```

В будущем должны быть возможны:

```text
YandexMailProvider
GmailProvider
OutlookProvider
```

без изменения доменной логики.

------

## Синхронизация

Реализовать периодическую синхронизацию Яндекс.Почты.

Использовать Laravel Scheduler.

Синхронизация должна быть идемпотентной.

Повторный запуск не должен создавать дубликаты сообщений.

Хранить внешний идентификатор сообщения и необходимые данные для определения уже обработанных писем.

Не скачивать весь mailbox при каждом запуске.

На MVP достаточно регулярно получать новые письма.

------

## Настройки подключения

Данные подключения к Яндекс.Почте не хранить в коде.

Использовать `.env` / Laravel configuration.

Например:

```env
MAIL_PROVIDER=yandex

YANDEX_IMAP_HOST=imap.yandex.ru
YANDEX_IMAP_PORT=993
YANDEX_IMAP_ENCRYPTION=ssl
YANDEX_IMAP_USERNAME=
YANDEX_IMAP_PASSWORD=
```

Фактические параметры подключения проверить по актуальной документации Яндекс.Почты перед реализацией.

Не логировать пароль или другие секреты.

------

# 14. Очереди

Не выполнять длительный AI-анализ внутри HTTP request.

Использовать очереди.

Пример:

```text
Sync Yandex Mail
    ↓
Store Message
    ↓
Classify Message Job
    ↓
Identify Project Job
    ↓
Analyze Message Job
    ↓
Apply Event Job
    ↓
Create Manager Action
```

Конкретное количество Job можно изменить, если это упрощает архитектуру.

------

# 15. Логирование

Для каждого сообщения должна быть возможность понять:

```text
когда получено
↓
когда классифицировано
↓
какой проект выбран
↓
какой AI-анализ выполнен
↓
какое событие создано
↓
изменилось ли состояние проекта
↓
создано ли предложение менеджеру
```

AI-запросы и ответы логировать таким образом, чтобы можно было отлаживать систему.

При этом не допускать утечки секретов и credentials в логи.

------

# 16. AI Provider

Не привязывать бизнес-логику к Gemini.

Создать интерфейс примерно следующего уровня:

```php
interface AiAnalyzer
{
    public function analyze(MessageContext $context): AnalysisResult;
}
```

Создать реализацию для выбранного LLM provider.

На первом этапе допустимо использовать Gemini Flash.

В будущем должна быть возможность заменить:

```text
Gemini
→ OpenAI
→ Claude
→ другая модель
```

без изменения Project, Message, Event и ManagerAction.

------

# 17. Стоимость AI

Не отправлять AI запросы без необходимости.

Использовать детерминированные правила там, где они достаточны.

Например:

```text
известный email отправителя
→ проект определяется без LLM
```

или:

```text
очевидное техническое уведомление
→ не требуется полный анализ клиентского контекста
```

AI использовать там, где требуется понимание содержания.

------

# 18. Тестирование

Обязательно покрыть тестами:

## Почта

- импорт нового письма;
- повторный импорт того же письма;
- отсутствие дублей;
- обработка ошибки IMAP;
- корректное преобразование письма Яндекс.Почты в Message.

## Classification

- клиентское письмо;
- техническое уведомление;
- рассылка;
- неизвестное письмо.

## Project matching

- точное совпадение email;
- совпадение домена;
- совпадение thread;
- совпадение технического источника;
- отсутствие подходящего проекта;
- несколько возможных проектов.

## AI

Не делать тесты зависимыми от реального API.

Создать fake/mock AI provider.

Проверить:

- корректный результат;
- некорректный JSON;
- неизвестный event type;
- отсутствие project_id;
- низкую confidence.

## Manager actions

- создание предложения;
- подтверждение;
- редактирование;
- отклонение.

------

# 19. Не делать на первом этапе

Не реализовывать без отдельного требования:

- автоматическую отправку писем;
- Telegram;
- WhatsApp;
- полноценный CRM;
- сложный workflow engine;
- автономного AI-агента с правом выполнять произвольные действия;
- сложную аналитику;
- RAG/vector database;
- fine-tuning;
- микросервисную архитектуру;
- интеграцию с Gmail/Outlook вместо Яндекс.Почты.

Главная цель MVP — проверить гипотезу на реальной почте.

------

# 20. Критерий успеха MVP

Система должна позволять взять поток реальных писем одного менеджера и для каждого письма получить:

```text
Это письмо относится к проекту X
        ↓
Вот что произошло
        ↓
Вот актуальное состояние
        ↓
Менеджеру нужно / не нужно вмешаться
        ↓
Если нужно вмешаться:
вот предлагаемое действие
        ↓
если нужен ответ:
вот draft ответа
```

Менеджер должен иметь возможность проверить и исправить результат.

------

# 21. Экспериментальные метрики

Система должна сохранять данные, позволяющие оценить гипотезу.

Минимально измерять:

- количество полученных писем;
- количество технических писем;
- количество клиентских писем;
- количество писем, для которых проект определён автоматически;
- количество писем без определённого проекта;
- количество корректно определённых событий;
- количество событий, требующих участия менеджера;
- количество ложных предложений;
- количество draft ответов;
- количество draft ответов, принятых без изменений;
- количество draft ответов, отредактированных менеджером;
- количество предложений, отклонённых менеджером.

Особенно важно сохранять факт изменения результата менеджером.

Например:

```text
AI:
project = Project A

Manager:
project = Project B
```

или:

```text
AI:
requires_manager = true

Manager:
requires_manager = false
```

Это позволит использовать реальные исправления менеджера для последующего улучшения правил и промптов.

------

# 22. Детерминированные правила и AI

Разделять два типа логики.

## Детерминированные правила

Используются для:

- известных email;
- доменов;
- технических источников;
- идентификаторов Redmine/Jira;
- известных шаблонов;
- очевидных системных уведомлений.

## AI

Используется для:

- понимания содержания;
- определения смысла сообщения;
- определения события;
- определения необходимости участия менеджера;
- формирования краткого summary;
- подготовки draft ответа.

Не использовать AI там, где решение надёжно принимается обычным правилом.

------

Менеджер должен иметь возможность создать проект и настроить правила обработки.

Для проекта предусмотреть:

```text
Проект: Интернет-магазин А

Основная информация
────────────────────────
Название
Описание
Статус

Контакты
────────────────────────
Email клиентов
Email сотрудников
Домены

Технические источники
────────────────────────
Redmine
Jira
Aspro

────────────────────────
```

------

# 24. Работа с неизвестными письмами

Если система не уверена в классификации или проекте, она не должна принимать решение на основании догадки.

Например:

```text
classification = unknown
project_id = null
```

Такое письмо должно отображаться менеджеру для ручной классификации.

После ручной классификации сохранить результат.

В будущем эти данные могут использоваться для улучшения правил.

# 25. Безопасность

Почтовые данные могут содержать конфиденциальную информацию.

Обязательно:

- не хранить credentials в Git;
- использовать `.env`;
- не выводить пароли в логи;
- не отправлять в LLM данные, которые не нужны для анализа;
- ограничивать контекст AI только необходимыми письмами и данными проекта;
- не давать AI права самостоятельно отправлять письма в MVP;
- валидировать все результаты AI перед записью в БД.

# 27. Definition of Done

MVP считается готовым, когда:

1. Реальная Яндекс.Почта подключается к системе.
2. Новые письма автоматически импортируются.
3. Повторная синхронизация не создаёт дубликаты.
4. Письма классифицируются.
5. Технические уведомления не считаются автоматически клиентскими.
6. Письма сопоставляются с проектами.
7. Для письма формируется нормализованное событие.
8. Состояние проекта может измениться на основании события.
9. Определяется необходимость участия менеджера.
10. При необходимости создаётся ManagerAction.
11. Для ответа создаётся draft.
12. Менеджер может изменить или отклонить результат.
13. AI не отправляет письмо самостоятельно.
14. Все основные сценарии покрыты automated tests.
15. Есть журнал обработки, позволяющий понять, почему система приняла конкретное решение.
16. Собираются метрики, необходимые для оценки гипотезы.

------

# 28. Правило для coding agent

Не начинать сразу с написания большого количества кода.

Сначала:

1. проанализировать репозиторий;
2. определить существующие Laravel conventions;
3. определить отсутствующие компоненты;
4. проверить существующую структуру проекта;
5. создать `docs/IMPLEMENTATION_PLAN.md`;
6. описать предлагаемые модели, миграции, сервисы, jobs и интерфейсы;
7. показать план в конце первого этапа работы;
8. после этого реализовывать проект по Phase 1 → Phase 8.

Если обнаруживается архитектурное решение, которое противоречит этому документу, остановиться и явно описать проблему в плане вместо молчаливого изменения требований.

Главный приоритет:

**рабочий проверяемый MVP > количество функций > архитектурная сложность.**
